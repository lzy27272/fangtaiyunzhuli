任务编号：`OTA-AUTOMATION-V0.1`
创建日期：2026-07-22
当前状态：业务设计已确认（DESIGN-1.5）/ 技术板块T0至T5全部确认 / OFFLINE BROWSER SESSION SKELETON COMPLETE / I1 LICENSE EVIDENCE MISSING / REAL PMS LOGIN BLOCKED / REAL CONNECTORS BLOCKED / PRODUCTION NO-GO
当前确认节点：已完成程序内PMS登录的离线安全骨架；后台、API、Worker和独立浏览器助手之间只允许不透明授权句柄或SecretStore引用，真实登录、Secret解析、网络、采集与企微发送仍BLOCKED

## 一、任务目标

先以独立后台建立OTA自动化能力，保证试点连续运行；后续通过统一登录、API和事件融入AI中台。业务链路如下：

```text
携程 / 美团OTA房态与订单
            +
酒店PMS房态与订单
            ↓
标准化、房型映射与库存对账
            ↓
每小时增量预订与剩余库存分析
            ↓
异常判断、任务闭环与企业微信群推送
```

首要业务结果：

1. 统计每小时新增预订间夜，并区分当日到店和远期到店。
2. 展示当前剩余房型和房间数量。
3. 比较PMS、携程和美团的房态是否符合配置的库存策略。
4. 每小时自动生成分析结果并推送到企业微信群。
5. 超卖等严重风险不等待整点，发现后立即告警。

## 二、阶段架构与兼容约束

已确认V0.1先作为独立后台运行，以免现有AI中台开发进度影响两家门店连续测试：

- 独立后台拥有自己的Web、API、数据库、连接器Worker、账号权限、任务、通知、审计和发布周期。
- PMS系统、携程、美团及门店参数均在独立后台配置；测试通过后新增门店无需修改业务代码。
- 独立后台不直接读写AI中台数据库，试点期间不对同一业务对象实行双写。
- 现有AI中台的组织、一人多岗、租户隔离、标准中心、规则与AI职责分离等冻结模型，作为未来融合时的兼容边界，不是V0.1运行时依赖。
- 后续优先通过SSO/统一入口、版本化API和领域事件融入AI中台；是否物理合库另行评审。
- OTA经营事实、P1和小时简报继续由确定性规则生成，AI只提供建议，不改写事实。

## 四、第一板块：数据接入与登录态（已确认）

### 4.1 平台范围

- 携程eBooking。
- 美团酒店商家后台。
- 酒店PMS，具体产品名称、版本和接入能力待补充。

### 4.2 OTA登录方案

携程和美团均采用“专用运营账号 + 首次人工登录 + 加密复用完整浏览器会话”的过渡接入方案：

1. 管理员首次人工登录并完成短信、验证码或设备验证。
2. 系统保存完整授权会话，不仅保存单一Cookie，还包括平台实际需要的浏览器存储和安全令牌。
3. 携程和美团分别使用独立账号、独立浏览器上下文和独立加密会话，禁止共用。
4. 定时采集前检查登录状态；失效后立即停止该平台采集，并通知管理员重新授权。
5. 不绕过验证码、短信验证、设备校验或平台风控。
6. 不在数据库、页面或日志中明文展示账号密码、Cookie、Token或Webhook密钥。

### 4.3 第一阶段能力边界

- 只读采集订单、订单变更、房型库存、关房/售罄状态和数据更新时间。
- 不自动修改OTA房量。
- 不自动调价。
- 不自动确认或取消订单。
- 不抓取消费者端公开页面。
- Excel或平台导出文件作为自动采集故障时的备用输入。
- 未来取得正式API后，仅替换平台连接器，不改动分析、规则、任务和页面模型。

### 4.4 已确认的采集频率、水位与降级

- PMS同步：每5分钟一次。
- 携程、美团：先尝试每15分钟一次；如触发平台风控或稳定性不足，调整为每30分钟一次。
- 数据过期阈值为`2 × 当前采集周期＋2分钟`。
- 明确登录失效首次确认即进入数据不可用P1；普通网络或解析错误连续两个应执行周期失败才进入不可用P1。
- 每个整点HH:00协调采集，来源观察时间最大允许偏差2分钟；HH:05冻结事实，HH:06发送。
- 来源不完整时仍按时发送降级简报，受影响指标显示“无法判断”，不得用0或旧值代替，也不得无限等待。
- 小时简报：数据统一截止于整点00分钟，每个整点后第6分钟发送。
- 超卖等严重风险：发现后立即告警。

### 4.5 统计原则

“每小时新增预订”应根据订单创建时间、修改时间和取消事件计算，不能只通过两次库存快照的差值推算。

### 4.6 已确认的PMS与OTA接入后台配置

- 独立OTA后台提供“PMS与OTA接入配置”页面，按门店独立配置PMS、携程和美团连接，无需修改代码或重新发版。
- PMS配置选择已支持的连接器适配器和接入方式（正式API、只读数据库、自动报表或官方导出文件），维护厂商、版本、地址/数据源、营业日字段、采集频率和加密凭据引用；支持后台连通性与权限测试。
- 携程、美团配置选择对应平台连接器，维护专用运营账号标识、启用状态、采集频率、最近成功时间和加密浏览器会话状态；管理员可在受控浏览器中发起首次登录或重新授权。
- 后台只配置已支持连接器的参数，不允许运行任意脚本或接入未审核的网页地址；新增PMS厂商或平台能力通过新增适配器实现。
- 密码、Cookie、Token、Webhook等密钥只可在受控表单写入并加密保存，配置页、日志和审计导出均不回显明文。
- 每次配置变更、连通性测试、启停和重新授权均记录操作人、门店、来源、时间、结果和失败原因。

## 五、第二板块：房型映射与库存对账（已确认）

### 5.1 当前建议

使用集团标准房型作为中间层：

```text
PMS房型 → 集团标准房型 ← 携程房型/售卖产品
                       ← 美团房型/售卖产品
```

OTA的含早、无早、连住、会员价等售卖产品可能共享同一实体房型库存，不能按产品数量重复累计。

库存策略模型可保留以下三种类型：

1. 完全同步：OTA应售数量等于PMS可售数量。
2. 保留房：OTA应售数量等于PMS可售数量减去保留房数。
3. 渠道配额：OTA应售数量等于PMS可售数量和渠道最大配额中的较小值。

试点门店当前已确认采用“完全同步”：

- 携程和美团的应售房量始终等于PMS对应实体房型的当前可售房量。
- 不故意保留1至2间房。
- 携程和美团不分别设置渠道最大可售数量。
- 对账公式为：`OTA应售数量 = PMS当前可售数量`。
- “保留房”和“渠道配额”仅保留为未来可扩展策略，不作为本次试点的实际经营规则。

同一实体房型可以在携程、美团配置套餐、含早、无早、会员价或连住等多个售卖产品。这些产品共享同一个实体房型的实际库存，映射和统计规则如下：

- 每个OTA售卖产品必须映射到唯一的集团标准房型，并归入同一个实体库存池。
- 各售卖产品的库存明细单独保留，用于发现单个产品关售、少放或映射错误。
- 收益、今日可售、售罄和超卖风险均按实体库存池计算；禁止将多个售卖产品显示的库存相加。
- 当同一库存池下某个售卖产品的库存或开关房状态与PMS不一致时，记录为产品级对账异常；实体库存不因该产品的显示库存被重复扣减。

建议的对账状态：

- 正常匹配。
- OTA多放，存在超卖风险。
- OTA少放，存在少卖风险。
- PMS售罄但OTA仍有房。
- PMS有房但OTA关房。
- 房型未映射。
- 数据过期。
- 采集失败，无法判断。

采集失败或数据过期时必须显示“无法判断”，不得使用0或旧数据伪装当前结果。

### 5.2 已确认的库存政策

1. 携程、美团的应售房量始终与PMS对应实体房型的当前可售房量一致。
2. 不故意保留1至2间房。
3. 携程和美团不分别设置最大可售数量。

### 5.3 已确认的售卖产品共享库存规则

1. 同一实体房型可在携程或美团建立套餐、含早、无早、会员价、连住等多个售卖名称或产品。
2. 多个售卖产品共享同一个实体房型的实际库存。
3. 对账、汇总和经营指标按实体库存池计算，不将多个售卖产品库存相加。

## 六、第三板块：每小时分析指标（已确认）

### 6.1 已确认的营业日口径

- 所有“今日”指标均以PMS营业日为准，不以系统自然日零点作为切换边界。
- 每条订单事件、房态快照、收益快照和小时简报均保存PMS营业日字段。
- PMS切换营业日前，跨自然日零点后的订单、收入和库存仍归属PMS当前营业日。
- PMS营业日切换时刻不设固定值；凌晨2点至7点之间仍以实际夜审完成情况和PMS当前营业日字段为准。
- 系统以连续两次成功PMS快照中的营业日字段变化识别“营业日切换”事件，记录实际生效时间；切换后生成新营业日的首个小时快照。

### 6.2 已确认的营业额口径

- “总营业额”只统计PMS归类为房费的收入。
- 钟点房收入属于房费收入，计入“总营业额”。
- 早餐、餐饮、服务费、押金及其他非房费项目不计入“总营业额”。
- 取数以PMS房费明细或房费汇总字段为准，不以OTA订单总价替代。
- 钟点房单列笔数和收入，计入总营业额及其目标完成进度。
- 钟点房不计入过夜房的今日已售、入住率、ADR或RevPAR；这些指标使用过夜房房费和过夜房房晚计算。

### 6.3 已确认的今日已售口径

- “今日已售”按PMS当前营业日的过夜已入住和已确认预订房间数统计。
- 计入在住及已确认但未入住的预订。
- 不计入取消、未到店（No-show）和钟点房。
- “今日可售”与入住率的过夜房分母均以此口径计算。

### 6.4 已确认的每日目标口径

- 每日“目标任务”和“目标均价”由收益管理人员按门店和PMS营业日预先配置。
- 当前阶段AI不自动生成或修改目标，仅基于已生效目标解释完成进度和价格状态。
- 目标配置变更必须保留版本、生效时间、配置人和变更原因，以支持小时简报追溯。

### 6.5 已确认的旺季节奏口径

- “旺季标准”拆分为收益进度与售卖进度两条节奏曲线，分别计算偏差。
- 节奏曲线按门店、季节、星期和节假日版本化，由收益管理人员配置。
- 未配置适用节奏曲线时，小时简报显示“暂未配置标准”，AI不得虚构旺季判断。
- 节奏偏差小于`-2.0个百分点`为“落后”，`-2.0至+2.0个百分点`为“符合节奏”，大于`+2.0个百分点`为“领先”。
- ADR低于目标均价90%为“偏低”，90%至110%为“合理”，高于110%为“偏高”。
- PMS实体房型可售为0可以称“售罄”；未配置适用售罄节奏时不得称“提前售罄”。

### 6.6 已确认的小时统计窗口

- 小时统计数据截至整点00分钟，与上一小时相同整点截止时点比较，例如`17:00→18:00`。
- 小时订单、取消、营业额变化和房量变化的归属窗口统一为`(上一整点, 当前整点]`，避免边界数据重复统计。
- 小时简报的实际发送时刻独立于数据截止时刻；生成时必须展示统计截止时间和各来源最新成功更新时间。

### 6.7 已确认的小时简报发送时刻

- 每个整点后第6分钟发送小时简报，例如数据截至18:00，于18:06发送。
- 发送时刻不改变统计边界；18:01及之后发生的订单和变化归入下一小时窗口。
- PMS切换至新营业日后的首份简报不与上一营业日画升降箭头，实时变化和每时速度显示“不适用（营业日首报）”。

### 6.8 已确认的间夜展示口径

- 企业微信群的订单情况以间夜为唯一展示单位，不展示订单笔数或“单”。
- 按携程、美团等渠道分别展示新增间夜、取消/减少间夜和净变更间夜。
- 新增间夜按入住日期拆分为当日间夜和远期间夜。
- 日累计和小时窗口使用同一口径；小时窗口遵循`(上一整点, 当前整点]`。
- “取消/减少间夜”包含整单取消，以及改期、缩短入住和减房产生的负向间夜；后台分别保留整单取消和订单调整减少原因。
- 负向间夜按取消或订单修改事件实际发生时间归属当前窗口，不要求其原始创建时间也位于该窗口。
- 净变更间夜为本窗口新增间夜减去取消/减少间夜，直接用于库存、入住率和收入影响分析。
- 外部订单号和订单事件仍在系统内部保存，用于去重、追溯和将多间、多晚订单正确拆分为间夜，但不在微信群简报展示。

### 6.9 已确认的日累计口径

- “今日整体”从PMS当前营业日实际切换成功后开始累计，到当前整点统计截止时结束。
- 下一次PMS营业日切换后，自动开始新一轮累计。
- 日累计与小时窗口均以PMS营业日字段关联，避免夜审前后发生自然日混算。

### 6.10 已确认的收入归属口径

- 总营业额、ADR、RevPAR和目标完成进度只统计当前PMS营业日的房费。
- 多晚订单按实际入住日拆分房费归属；不将整张远期订单总价提前计入当前营业日。
- 远期订单只进入新增、取消和净变更间夜分析，以及未来需求判断。

### 6.11 已确认的今日可售口径

- “今日可售”直接取PMS当前营业日的实际可售过夜房数量。
- 维修房、停用房、锁房等状态由PMS先行反映在可售数中。
- 独立OTA后台不使用酒店固定总房量减今日已售的方式自行推算今日可售。

### 6.12 已确认的有效可售总房量口径

- RevPAR和售卖进度的分母使用PMS当前营业日的有效可售总房量，不使用酒店固定总房数。
- PMS未提供有效可售总房量字段时，才使用同一快照的“今日已售过夜房＋今日可售过夜房”补齐。

### 6.13 已确认的迟到数据补记规则

- 小时简报发出后，如采集到归属已发时段的迟到订单、取消或修正数据，不修改历史群消息。
- 下一小时简报单列“补记上时段”的新增间夜、取消/减少间夜、净变更间夜和收入影响。
- 系统保留原报表、补记记录、数据来源和计算版本，支持审计和重算。

### 6.14 已确认的核心计算公式

- 总营业额 = 当前PMS营业日的房费收入，包含钟点房；远期订单不提前计入。
- 过夜房费 = 当前PMS营业日房费收入减去钟点房收入。
- 今日已售 = 当前PMS营业日的过夜在住房间数加已确认未入住预订房间数。
- 今日可售 = PMS当前营业日实际可售过夜房数量。
- 有效可售总房量 = PMS当前营业日有效可售总房量；PMS未提供时，使用同一快照的今日已售过夜房加今日可售过夜房。
- ADR = 过夜房费 ÷ 今日已售；今日已售为0时显示“不适用”。
- RevPAR = 过夜房费 ÷ 有效可售总房量；分母为0时显示“不适用”。
- 目标完成进度 = 总营业额 ÷ 每日目标任务。
- 差额目标 = `max(每日目标任务 - 总营业额, 0)`。
- 剩余每间所需均价 = 差额目标 ÷ 今日可售；今日可售为0时显示“不适用”。
- 售卖进度 = 今日已售 ÷ 有效可售总房量。
- 小时变化 = 当前整点快照值减上一整点快照值；订单流量使用同一小时窗口内的新增、取消和净变更间夜。
- 旺季偏差 = 当前收益或售卖进度减适用节奏曲线标准；无适用曲线时显示“暂未配置标准”。

### 6.15 已确认的展示精度与异常值

- 所有计算使用Decimal原值，不先四舍五入。
- 金额、ADR和RevPAR展示2位小数；百分比和百分点展示1位，采用`HALF_UP`。
- 正变化使用`↑`、负变化使用`↓`、无变化使用`→0`。
- 负收入、负房量或超过合理范围的指标不得静默截断，必须标记一致性异常并停止相关经营判断。

## 七、第四板块：异常规则与任务闭环（已确认）

### 7.1 已确认的P1房态不匹配风险告警

- 当任一携程或美团售卖产品的实际可售房量大于PMS对应实体房型可售房量时，立即触发P1超卖风险。
- PMS对应实体房型可售为0而OTA仍有可售房时，同样属于P1超卖风险。
- 当任一携程或美团售卖产品的实际可售房量小于PMS对应实体房型可售房量时，立即触发P1房态不匹配风险，标记为OTA少放风险。
- 两类P1房态不匹配风险均立即推送企业微信群，不等待整点小时简报。
- 告警内容至少包含门店、实体房型、渠道及售卖产品、风险类型（OTA多放/OTA少放）、PMS可售、OTA可售、差额、来源更新时间和发现时间。

### 7.2 已确认的P1任务处置规则

- P1房态不匹配风险自动创建任务，指派给门店配置的当班处理岗位。
- 任务要求在10分钟内提交处理说明；仅查看或认领不算“已处理”。
- V0.1只执行告警、任务创建和审计，不自动修改OTA房量、价格或订单。

### 7.3 已确认的P1去重、升级与恢复规则

- 同一P1异常在未恢复期间不按采集频率重复刷群。
- 首次出现时立即告警并创建任务。
- 任务超过10分钟仍未提交处理说明时，再次催办并升级至门店负责人；V0.1只升级一次。
- P1方向从“OTA多放”直接翻转为“OTA少放”或反向翻转时，原事件标记`REPLACED`且不发送恢复，新方向立即作为新P1告警并标记“风险类型切换”。
- 异常恢复时发送一次恢复通知，并记录恢复时间、恢复前后房态和处理结果。

### 7.4 已确认的P1数据不可用告警

- 任一PMS、携程或美团连续两个采集周期失败、登录失效或数据过期时，立即触发P1数据不可用企微告警和任务。
- 小时简报中受影响来源和指标明确显示“无法判断”，不使用0或旧数据代替。
- 数据不可用恢复后，沿用P1恢复通知和审计规则。

### 7.5 已确认的P2经营偏差处理

- 收益进度与售卖进度落后作为P2经营偏差，随整点简报展示，并给出AI经营建议。
- V0.1不为P2经营偏差自动建任务或升级；只有P1异常自动创建任务。
- P2判断必须基于已配置的收益和售卖节奏曲线；缺少适用曲线时不生成P2结论。

### 7.6 已确认的P1任务关闭复核

- P1房态不匹配任务在处理人填写处理说明后，仍须由下一次成功采集复核PMS与OTA房态已恢复一致，才自动关闭并发送恢复通知。
- P1数据不可用任务在来源完整采集成功、数据达到新鲜度要求且重新执行房态对账不存在不匹配后，由系统自动关闭并发送恢复通知，不要求人工补交处理说明。
- 数据不可用恢复前已经发生的超时升级永久保留，不因自动关闭删除。
- 人工不能仅靠点击关闭绕过系统复核。

## 八、第五板块：企业微信群推送（已确认）

### 8.1 已确认的企业微信推送通道

- V0.1使用企业微信群机器人Webhook进行单向推送。
- Webhook作为密钥加密保存，不写入代码、日志、数据库明文字段或群消息。
- V0.1暂不支持在群内回复、认领任务或修改规则。
- 推送使用消息发件箱和唯一推送键，任务重试不重复发送同一份简报或告警。

### 8.2 已确认的接收群范围

- 小时收益简报和P1告警统一推送至同一个门店运营群。
- 消息标题和类型区分小时简报、P1首次告警、P1超时升级和P1恢复通知。
- 每个门店独立配置其运营群Webhook，避免跨门店误投递。

### 8.3 已确认的群内@提醒规则

- 小时收益简报、P1首次告警、P1超时升级和P1恢复通知均@门店运营群所有成员。
- 推送适配器必须使用企业微信群机器人支持的全员提醒形式，并在上线UAT中验证实际触达效果。
- 如全员提醒未成功触达，应记录为推送校验失败并进入运维排查，不得静默视为成功。

### 8.4 已确认的消息版式

- 小时收益简报固定采用六段版式：今日压力、今日进度、实时经营对比、收益判断、订单情况汇报、AI经营建议。
- P1单独发送精简即时告警，不等待完整小时简报。
- P1告警发出后，下一整点仍发送完整小时简报，并展示未恢复P1的当前状态。

### 8.5 已确认的P1即时告警字段

- P1即时告警固定包含风险级别与类型、门店、实体房型、渠道和售卖产品、PMS可售、OTA可售、差额、来源更新时间、发现时间和10分钟处理截止时间。
- P1内容使用结构化字段渲染，保证告警原因可追溯且不由AI改写关键数值。

### 8.6 已确认的小时简报补发规则

- Webhook恢复后，已过时但未送达的小时简报也必须补发，不得丢弃。
- 补发顺序为：先发送当前仍有效的P1，再发送已送达首告但未送达的恢复通知，最后按原统计截止时间顺序补发全部小时简报。
- Webhook故障期间已经自愈且首告从未送达的陈旧P1不再补发，标记`SKIPPED_OBSOLETE`并保留完整审计，避免冒充当前风险。
- 补发的小时简报必须显著标记“补发”，同时展示原统计截止时间与实际补发时间，避免被误解为当前实时数据。

### 8.7 已确认的投递失败处理

- Webhook首次发送失败后额外重试3次，即最多尝试4次；退避时间依次为30秒、2分钟、5分钟并加入小抖动。
- 4次尝试全部失败后只创建一个P1推送失败任务。
- Webhook恢复后，按已确认规则补发仍有效的P1告警和全部未送达小时简报。
- 每次投递尝试、平台返回结果、实际送达时间和补发关系均保留审计记录。
- 接受企微Webhook的at-least-once语义；网络响应丢失时可能产生远端重复，重试必须使用同一冻结正文和短消息编号，结果不明确时记录`AMBIGUOUS`。

## 九、第六板块：页面与角色权限（已确认）

### 9.1 已确认的独立后台页面范围

- V0.1提供独立登录入口，以及PMS与OTA接入配置、实时经营监控、房型/目标/节奏配置、简报与告警历史四个独立后台页面。

- 企业微信群只负责接收消息，不承担配置或任务处理。

### 9.2 已确认的配置与处置职责

- 房型映射、每日目标和节奏曲线仅由独立后台`REVENUE_MANAGER`收益管理角色在配置门店范围内维护。
- PMS与OTA接入配置、Webhook、OTA账号及登录态仅由平台管理员维护。
- 门店运营人员只可查看监控/历史，并处理分配给自己的P1任务。

### 9.3 已确认的数据范围和租户门店管理

- 独立后台保留每条业务数据的`tenant_id`和门店标识；普通门店运营人员仅查看和处理配置门店的数据。
- 管理员账号可在独立后台配置租户、门店及其关系；新增门店启用后由动态调度发现，不修改代码或部署配置。
- 管理员的配置写权限与五类角色的集团级只读权限分开计算，不能由只读能力推导写权限。

### 9.4 已确认的集团级跨租户查看范围

- 管理员、OTA运营助理、OTA运营经理、CEO和区域经理可跨租户查看OTA经营明细，无需逐租户人工授权。
- 该能力为上述岗位固有的集团级数据范围，不向其他岗位开放。
- 系统在服务端执行逐租户隔离查询并聚合结果；不得通过前端隐藏或通用数据库绕过实现。
- 所有跨租户查询与查看行为必须记录操作人、角色、查询条件、涉及租户和时间；V0.1不开放跨租户导出，未来如需开放，必须另设独立权限、范围限制和审计后再评审。

### 9.5 已确认的集团级岗位操作边界

- 管理员、OTA运营助理、OTA运营经理、CEO和区域经理的跨租户权限仅限监控、简报和告警历史的只读查看。
- 房型映射、目标/节奏、Webhook、登录态及P1任务处置仍按独立后台既定配置权限和门店范围执行。
- 该独立后台角色规则不改变AI中台或其他系统中的既有权限。

### 9.6 已确认的本地账号与自动化运行身份

- 本地人员账号只用于登录后台、配置、查询和处理任务，不直接承担数据采集或企业微信发送。
- PMS凭据、携程/美团浏览器会话和企微Webhook按租户、门店、来源及用途独立加密保存，不复用人员登录密码或会话。
- 调度器、采集Worker、分析任务和投递Worker使用不可交互的服务身份持续运行，不能通过登录页登录。
- 人员退出后台、Access Token到期或浏览器关闭不停止已启用门店的数据抓取、分析和自动推送。
- 来源授权失效时只暂停受影响来源并触发P1；自动化启停由门店及连接器开关控制。
