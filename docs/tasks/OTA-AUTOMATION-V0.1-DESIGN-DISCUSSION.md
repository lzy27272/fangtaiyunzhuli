## 一、任务目标

在中台增加OTA自动化能力，形成以下业务链路：

```text
携程 / 美团OTA房态与订单
            +
酒店PMS房态与订单
            ↓
标准化、房型映射与库存对账
            ↓
每小时增量预订与剩余库存分析
            ↓
异常判断、任务闭环与企业微信群推送
```

首要业务结果：

1. 统计每小时新增加的预订数量，并区分当日到店和远期到店。
2. 展示当前剩余房型和房间数量。
3. 比较PMS、携程和美团的房态是否符合配置的库存策略。
4. 每小时自动生成分析结果并推送到企业微信群。
5. 超卖等严重风险不等待整点，发现后立即告警。

## 二、既有架构约束

本任务是新的业务数据入口和管理闭环扩展，不改变现有冻结模型：

- 组织与权限模型。
- 一人多岗模型。
- 租户和门店数据隔离模型。
- 标准中心模型。
- 企业规则中心与AI分析职责分离。
- 任务、通知和审计均服从现有组织数据范围。

## 四、第一板块：数据接入与登录态（已确认）

### 4.1 平台范围

- 携程eBooking。
- 美团酒店商家后台。
- 酒店PMS，具体产品名称、版本和接入能力待补充。

### 4.2 OTA登录方案

携程和美团均采用“专用运营账号 + 首次人工登录 + 加密复用完整浏览器会话”的过渡接入方案：

1. 管理员首次人工登录并完成短信、验证码或设备验证。
2. 系统保存完整授权会话，不仅保存单一Cookie，还包括平台实际需要的浏览器存储和安全令牌。
3. 携程和美团分别使用独立账号、独立浏览器上下文和独立加密会话，禁止共用。
4. 定时采集前检查登录状态；失效后立即停止该平台采集，并通知管理员重新授权。
5. 不绕过验证码、短信验证、设备校验或平台风控。
6. 不在数据库、页面或日志中明文展示账号密码、Cookie、Token或Webhook密钥。

### 4.3 第一阶段能力边界

- 只读采集订单、订单变更、房型库存、关房/售罄状态和数据更新时间。
- 不自动修改OTA房量。
- 不自动调价。
- 不自动确认或取消订单。
- 不抓取消费者端公开页面。
- Excel或平台导出文件作为自动采集故障时的备用输入。
- 未来取得正式API后，仅替换平台连接器，不改动分析、规则、任务和页面模型。

### 4.4 推荐频率（待最终业务确认）

- PMS同步：每5分钟一次。
- 携程、美团：先尝试每15分钟一次；如触发平台风控或稳定性不足，调整为每30分钟一次。
- 小时简报：每个整点后的第8分钟生成。
- 超卖等严重风险：发现后立即告警。

### 4.5 统计原则

“每小时新增预订”应根据订单创建时间、修改时间和取消事件计算，不能只通过两次库存快照的差值推算。

## 五、第二板块：房型映射与库存对账（沟通中）

### 5.1 当前建议

使用集团标准房型作为中间层：

```text
PMS房型 → 集团标准房型 ← 携程房型/售卖产品
                       ← 美团房型/售卖产品
```

OTA的含早、无早、连住、会员价等售卖产品可能共享同一实体房型库存，不能按产品数量重复累计。

每个门店、房型和渠道允许配置一种库存策略：

1. 完全同步：OTA应售数量等于PMS可售数量。
2. 保留房：OTA应售数量等于PMS可售数量减去保留房数。
3. 渠道配额：OTA应售数量等于PMS可售数量和渠道最大配额中的较小值。

建议的对账状态：

- 正常匹配。
- OTA多放，存在超卖风险。
- OTA少放，存在少卖风险。
- PMS售罄但OTA仍有房。
- PMS有房但OTA关房。
- 房型未映射。
- 数据过期。
- 采集失败，无法判断。

采集失败或数据过期时必须显示“无法判断”，不得使用0或旧数据伪装当前结果。

### 5.2 等待产品负责人确认的问题

1. 目前携程、美团的房量是否要求与PMS剩余房量完全一致？
2. 是否会故意保留1至2间房不放到OTA？
3. 携程和美团是否分别设置不同的最大可售数量？
4. 同一个实体房型是否在OTA上建立多个名称或套餐，例如含早、无早、连住或会员产品？
